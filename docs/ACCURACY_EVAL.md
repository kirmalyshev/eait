# Accuracy eval — capture protocol

How to produce the weighed-meal fixture set (issue #6) and read the numbers it yields.

Every accuracy change in this repo is judged against this set. Without it, "the new prompt is
better" is an opinion. With it, it is a diff in kcal MAPE.

## Why weighed, and why this is the blocking step

The eval has run since 2026-07-22, but never against a scale:

| Fixture source | What it measures | Limit |
|---|---|---|
| `data/food-photos/` (22 real meals) | agreement with another LLM's guess | ground truth generated by Fable 5 — **circular** |
| Nutrition5k (30 dishes, `scripts/fetch-nutrition5k.ts`) | model capability on US cafeteria trays | real scale truth, but **not the cuisine our users eat** |
| **weighed meals (this doc)** | **absolute error on the food actually being logged** | needs a kitchen scale and a human |

Only the third one can answer "how wrong is the bot for *this* user, on *this* food". It is the
one thing no script can produce on its own — hence the protocol below.

## What you need

- A kitchen scale reading to 1 g. Any €12 model.
- Your phone.
- ~20 meals. One per meal, over a few days. Around 5 minutes of extra effort each.

## The protocol

For each meal, **before you eat it**:

1. **Weigh each component as it goes onto the plate.** Zero the scale, add the component, write
   down the number. Weigh what you will actually eat — the portion, not the pot.
2. **Weigh AS SERVED, cooked.** 100 g of dry rice becomes ~300 g cooked. The food table is
   per-100-g-as-served for exactly this reason, so weighing the cooked portion is what makes the
   lookup correct. If you weighed something raw and ate it cooked, say so in the name and use a raw
   entry, or skip that meal — a mismatch here is a 3x error, far larger than anything being measured.
3. **Count the oil.** The tablespoon of oil in the pan is 10–15 g and ~120 kcal — often more than
   the vegetables it cooked. Weigh the bottle before and after if that is easier.
4. **Photograph the finished plate the way you would send it to the bot.** Normal phone camera,
   normal angle, no special lighting. A staged overhead shot measures a photo you will never take.
5. **Record it:**

```bash
bun run scripts/add-fixture.ts --photo ~/Downloads/IMG_4821.jpg --name 2026-07-26-lunch \
  "chicken breast: 180" \
  "rice, cooked: 210" \
  "olive oil: 12" \
  "cucumber: 90"
```

The script prints the breakdown with each component's share of the meal's calories, then writes
`eval/<name>.jpg` + `eval/<name>.json`. Check the percentages before moving on — a mistyped weight
is invisible on its own line and obvious as a share ("olive oil 60%").

### Foods not in the table

`--foods` lists the ~100 single ingredients it carries. Anything composite or branded — pelmeni, a
jar of sauce, a protein bar — is deliberately **not** in there, because its numbers vary by
producer and a generic row would be invented precision. Give the package label instead:

```bash
  "pelmeni: 250 @ 275"              # kcal per 100 g
  "kefir 1%: 250 @ 40/3.4/4/1"      # kcal/protein/carbs/fat per 100 g
```

A label beats the table even for foods the table has — if you have the product in hand, use it.

If a component only gets a kcal figure, **the meal reports no macros at all**. That is deliberate:
summing the macros of the components that declared them would produce ground truth that is wrong
low, and the eval would score the missing grams as model error. kcal + total grams is still a
perfectly good fixture — they are the two numbers that matter most.

### Cover the hard cases too

A set of 20 clean single-plate photos will report an error rate the bot does not have in daily use.
Aim for a spread:

- plain single dishes (the easy baseline)
- mixed plates, 3+ components
- restaurant portions you did not cook — weigh what arrives, if you can
- a soup or stew, where volume hides mass
- a layered/tall dish (burger, sandwich, bowl) — the case #11's side-view prompt exists for
- one deliberately bad photo: dim, angled, half-eaten

## Running it

```bash
OPENROUTER_API_KEY=... bun run scripts/eval-meals.ts --runs 3
```

**This spends money** — one billed vision call per fixture × run × model. 20 fixtures × 3 runs is
60 calls. `--runs 3` is what makes the run-to-run spread column real; `--runs 1` prints `n/a` for it.

A/B two models or two prompts with `--models a,b`. Full flag list: `scripts/README.md`.

## Reading the report

```
model: x-ai/grok-4.5 (20 cases)
  kcal    MAE 125 · MAPE 42.2% · run spread 155 (20 cases with ≥2 runs)
  kcal    BIAS +16.5% (20 cases) · over-estimated in 75% of 20 cases
  portion MAPE 37% (20 cases)
  density MAPE 28% (20 cases)
  kcal error source: grams |ln| 0.3 vs density |ln| 0.2 — 56% of the error magnitude is grams, grams-dominated in 65% of 20 cases
  bias direction: portion +16.5% · richness 0% (20 cases)
  coverage: 20/20 fixtures evaluated · runs 60/60
```

- **MAPE** is the headline: typical error as a percentage. Published photo-only estimation sits at
  15–25%; anything under that band deserves suspicion before celebration.
- **BIAS** is the actionable one. MAE cannot tell a model that is uniformly 30% high from one that
  scatters ±30% — they score identically, but the first is a one-line prompt fix and the second is a
  hard modelling problem. A large signed bias is the cheapest accuracy win available, and deleting
  one over-cautious prompt line on that evidence moved kcal MAE 149 → 125.
- **kcal error source** splits each meal's error into portion (how many grams) and richness
  (kcal per gram), exactly, because `kcal = grams × density`. This is the number that decides which
  lever to pull — and the one #8 (nutrition-DB grounding) is gated on.
- **coverage** prints on stdout beside the report. Two models with different evaluated counts are
  **not comparable**: the dropped cases are the ambiguous photos, so a model that refuses more looks
  better on what remains.

Archive each run as an issue comment — model, date, flags, and the block above. A number with no
recorded conditions cannot be compared against the next one.

## Where the fixtures live, and what leaves the machine

`eval/` is gitignored by name. Photos of your food, and the ground truth beside them, are **never
committed** — the runtime's images-are-ephemeral invariant is about the bot, and these are dev
fixtures, but they are still your meals.

Two things to know:

- **The photos are uploaded to OpenRouter** on every eval run — that is the billed call. If a photo
  carries EXIF GPS, that goes with it. The script does not strip EXIF (that would mean an image
  dependency for a dev tool); if it matters to you, strip it before recording the fixture.
- **`add-fixture.ts` copies, never moves.** The original stays in your camera roll.

## Accuracy of the ground truth itself

Composition-table lookup is the same method the published datasets use — Nutrition5k weighed
ingredients and looked them up too — and it inherits the table's error: a few percent for staples,
more for anything variable (fat trim on meat, how much oil the pan kept rather than the food).

That is well below the ~40% model error being measured, so it does not threaten the comparison. It
does mean a 3% shift in a reported metric is noise, not a result.
